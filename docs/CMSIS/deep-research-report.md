# CMSIS-NN Compiler Options and Integration Formalisms in Z-Ant

## Scope and source basis

This report is grounded in the `feat/CMSIS-integration` branch of `ZantFoundation/Z-Ant`, with direct inspection of the current build system, CMSIS dispatch module, the `QLinearConv` operator implementation, the CMSIS wrapper, the quantization utilities, and the project’s own CMSIS integration guide. For the CMSIS side, it also uses Arm’s official CMSIS-NN repository and the generated API documentation on `arm-software.github.io`, especially the convolution wrapper documentation, buffer-size logic, compiler header, and the official build guidance. fileciteturn52file0L3-L3 fileciteturn51file0L3-L3 fileciteturn53file0L3-L3 fileciteturn54file0L3-L3 fileciteturn55file0L3-L3 fileciteturn56file0L3-L3 fileciteturn57file0L3-L3 fileciteturn27file0L3-L3 fileciteturn28file0L3-L3 citeturn10view0turn12view0turn13view0turn14view2

The most important framing point is that the branch does **not** treat CMSIS-NN as a generic drop-in library call. Instead, it implements a branch-specific calling contract around layout conversion, quantization parameter generation, weight packing, scratch-buffer allocation, and compile-time dispatch. That is why the question is not just “which flags are needed,” but also “which tensor and quantization formalisms must already be true when those flags are used.” fileciteturn54file0L3-L3 fileciteturn55file0L3-L3 fileciteturn56file0L3-L3

## How the current integration works in Z-Ant

At build time, `build.zig` parses the Zig build options for `target` and `cpu`, resolves them into the actual compilation target, and then conditionally injects CMSIS support into a wide set of artifacts when CMSIS is enabled: root unit tests, the code generator, generated-model executables, generated-model tests, the final static library, one-op generators/tests, extractor tools/tests, the benchmark executable, and the ONNX parser tests. Separately, the main `zant` module receives CMSIS include paths so that Zig code can `@cImport` CMSIS headers. In other words, CMSIS integration is wired high in the build graph, not only into the final deployment library. fileciteturn52file0L3-L3 fileciteturn58file0L3-L3

The current build entrypoint for CMSIS is `configureCmsisSupport()`. That function adds include paths for `third_party/CMSIS-NN`, `third_party/CMSIS_5/CMSIS/Core/Include`, `third_party/CMSIS-DSP/Include`, `third_party/CMSIS-DSP/PrivateInclude`, and a discovered Arm newlib include directory. It also compiles a curated set of CMSIS-NN convolution and support C files, plus one CMSIS-DSP source file. This matters because the integration is **manual**: Z-Ant is not simply invoking upstream CMSIS-NN CMake, it is recreating enough of it in Zig build logic to link the convolution path it needs. fileciteturn51file0L3-L3 fileciteturn44file0L3-L3 fileciteturn45file0L3-L3 fileciteturn46file0L3-L3

The explicit per-file C flags currently used for the CMSIS C sources are these:

```zig
const c_flags = &[_][]const u8{
    "-DOPTIONAL_RESTRICT_KEYWORD=__restrict",
    "-fbuiltin",
    "-Ofast",
    "-fno-math-errno",
};
```

Those are the **actual current CMSIS-specific compiler options** in the inspected integration entrypoint. fileciteturn51file0L3-L3

The branch’s own CMSIS guide shows the expected embedded build pattern on Cortex-M targets, for example with `thumb-freestanding` plus `cortex_m7` or `cortex_m4`, and `ReleaseSmall` on the Zig side. That is an important nuance: the guide’s top-level Zig build uses `-Doptimize=ReleaseSmall`, but `configureCmsisSupport()` still forces the CMSIS C translation units to `-Ofast`. So the current integration intentionally splits policy between the Zig application code and the CMSIS kernel code. fileciteturn57file0L3-L3 fileciteturn51file0L3-L3

On the operator side, `op_qlinearconv.zig` uses a compile-time dispatch function, `qlinearconv_lean()`, that checks `mod_cmsis.cmsisUsed()` and then either calls the CMSIS wrapper or falls back to Z-Ant’s native embedded implementation. The intended idea, as documented in `mod_cmsis.md`, is “use CMSIS only when the feature flag is enabled **and** the target is a Cortex-M architecture.” But the **current code** has `const targetIsCortex: bool = true;` hardcoded, so the architectural half of that decision is currently a placeholder rather than a real target check. fileciteturn54file0L3-L3 fileciteturn53file0L3-L3 fileciteturn61file0L3-L3

The current branch actually contains **two** CMSIS wrapper entrypoints. `qlinearconvWithTranspose()` is the path that explicitly converts between Z-Ant’s older NCHW-style expectations and CMSIS’s NHWC-style calling contract; `qlinearconv()` is the newer optimized path that assumes the tensors are already in CMSIS-friendly form. The optimized path explicitly extracts input/output as NHWC and weights as OHWI, while the transpose path performs a layout conversion before the call and a reverse conversion after it. The project’s own `CMSIS_GUIDE` confirms this: it tells users to generate NHWC ONNX models for CMSIS, and it also says that if they want the transpose-based path they must manually edit `op_qlinearconv.zig` to call `qlinearconvWithTranspose` instead of `qlinearconv`. fileciteturn55file0L3-L3 fileciteturn56file0L3-L3 fileciteturn57file0L3-L3 fileciteturn62file0L3-L3

Once the CMSIS path is selected, the wrapper performs the whole adaptation layer itself. It computes per-channel multipliers and shifts from the quantization scales, converts u8 zero-points into the signed s8 offset domain CMSIS expects, converts or zero-copies the bias depending on whether it is already `i32`, repacks the weights if needed, asks CMSIS for the required scratch-buffer size, allocates the `cmsis_nn_context`, and finally calls `arm_convolve_wrapper_s8`, `arm_depthwise_conv_wrapper_s8`, or a grouped-convolution loop that repeatedly calls the standard wrapper per group and then re-interleaves the results. That is the core of “how the current integration is happening.” fileciteturn55file0L3-L3 fileciteturn29file0L3-L3 fileciteturn30file0L3-L3 fileciteturn50file0L3-L3

## CMSIS-NN build options that matter for successful integration

The single most important CMSIS-NN build dial is **the target CPU / architecture feature selection**, not a CMSIS-NN-specific macro by itself. Arm’s own README says the normal library build flow expects a `TARGET_CPU=cortex-mXX` setting, and the library documentation explains that the optimized implementation is selected according to the architecture feature flags made available to the compiler. In practice that means the *real* switch is the Cortex-M CPU selection—Cortex-M4/M7 for DSP-oriented paths, Cortex-M55/M85 for Helium/MVE-oriented paths—not manually toggling random macros in isolation. fileciteturn27file0L3-L3 citeturn2view0

That architecture choice is not just about performance. It changes which CMSIS code bodies compile and which scratch-buffer formulas are used. For example, `arm_convolve_get_buffer_sizes_s8.c` and other support files branch on `ARM_MATH_MVEI` and `ARM_MATH_DSP`; the matrix-multiply support used by convolution does the same. So the correct CPU selection is part of the **correctness contract** as well, because different kernels have different workspace shapes, different fast paths, and different assumptions. In Z-Ant, the equivalent upstream `TARGET_CPU` dial is the combination of `-Dtarget=thumb-freestanding` and `-Dcpu=cortex_m4` or `-Dcpu=cortex_m7` shown in the CMSIS guide. If the intention later becomes Cortex-M55 or Cortex-M85, that CPU choice must change accordingly. fileciteturn30file0L3-L3 fileciteturn38file0L3-L3 fileciteturn57file0L3-L3

The second load-bearing option is the **optimization level**. The official CMSIS-NN build system sets `-Ofast` by default, and the README explicitly warns that low optimization degrades performance and that Helium builds at `-O0` may need `ARM_MATH_AUTOVECTORIZE`. Z-Ant already aligns with this by forcing `-Ofast` on the CMSIS C compilation units, regardless of the broader Zig optimization mode chosen for the rest of the project. That is a strong and correct design choice for preserving CMSIS kernel behavior. The related `-fomit-frame-pointer` question is already effectively covered, because Arm notes it is enabled by default at `-O` and higher. Since the current integration compiles CMSIS at `-Ofast`, there is no separate missing `-fomit-frame-pointer` requirement here. fileciteturn27file0L3-L3 citeturn9view0 fileciteturn51file0L3-L3

The third major issue is **builtin behavior under freestanding compilation**. Arm’s README is unusually explicit here: `-fno-builtin` hurts CMSIS-NN because the kernels rely heavily on optimized `memcpy` and `memset`, and `-ffreestanding` should also be avoided because it implies `-fno-builtin`. Z-Ant’s branch-specific answer is pragmatic: its guide still builds embedded artifacts as `thumb-freestanding`, but the CMSIS source files are compiled with `-fbuiltin` and the various artifacts call `linkLibC()`. That means the current integration is not following Arm’s recommendation literally, but it **is** compensating for the most important side effect of freestanding mode. For this branch, that compensation is one of the key “hidden” compiler requirements. fileciteturn27file0L3-L3 fileciteturn57file0L3-L3 fileciteturn51file0L3-L3 fileciteturn52file0L3-L3

The fourth current flag, `-DOPTIONAL_RESTRICT_KEYWORD=__restrict`, is very specifically a CMSIS-NN performance knob. In the official README, Arm says this can help DSP int4/int8 convolutions, especially on Cortex-M7, while Cortex-M4 and Cortex-M33 often see little or no benefit. In the CMSIS source tree, `OPTIONAL_RESTRICT_KEYWORD` is defined in `arm_nnsupportfunctions.h` and is used in convolution support functions such as `arm_nn_mat_mult_kernel_s8_s16.c`. Z-Ant currently enables it unconditionally for all CMSIS C files. That is acceptable, and it clearly aligns with M7-centric optimization, but it is worth understanding that it is a **performance formalism**, not a semantic one: the library works without it, but some DSP targets benefit. fileciteturn27file0L3-L3 fileciteturn26file0L3-L3 fileciteturn34file0L3-L3 fileciteturn51file0L3-L3

`ARM_MATH_AUTOVECTORIZE` is a different kind of switch. It is relevant only to Helium/MVE builds. In `arm_nn_mat_mult_nt_t_s8.c`, the MVE branch has one path guarded by `ARM_MATH_AUTOVECTORIZE` and another path using inline MVE assembly. Arm’s README also says that with only `-O0`, Helium targets need `ARM_MATH_AUTOVECTORIZE`. For the **current** Z-Ant branch, which documents Cortex-M4 and Cortex-M7 examples, that macro is not required today. But if the integration is meant to become a first-class Cortex-M55/M85 CMSIS-NN backend, then this macro needs to be treated as a real build option, not an afterthought. Right now I did not see it exposed in the inspected Z-Ant CMSIS build entrypoint. fileciteturn27file0L3-L3 fileciteturn38file0L3-L3 fileciteturn51file0L3-L3

The final CMSIS-NN compile-time options worth naming are `CMSIS_NN_USE_SINGLE_ROUNDING` and `CMSIS_NN_USE_REQUANTIZE_INLINE_ASSEMBLY`. Arm documents both in the official README. The first changes requantization behavior and can alter outputs; the second uses inline assembly for `arm_nn_requantize`, is faster on Cortex-M4, slower on others, and has had observed differences with Arm Compiler plus Cortex-M7. These are **not baseline integration requirements** for the current branch, and I did not see them wired into the current Z-Ant CMSIS build hook. But if the goal is a robust, configurable CMSIS-NN backend rather than a fixed-branch prototype, they should eventually be surfaced as explicit, documented toggles. fileciteturn27file0L3-L3 fileciteturn51file0L3-L3

## Non-flag requirements and integration formalisms

The biggest non-flag formalism is **tensor layout**. The official CMSIS-NN convolution wrapper documentation states that `arm_convolve_wrapper_s8` expects input/output tensors in `[N, H, W, C]` order and filter tensors in `[C_OUT, HK, WK, C_IN]` order. The depthwise wrapper documentation is different again: its filter format is `[1, H, W, C_OUT]`, and for the s8 depthwise wrapper the batch dimension is effectively treated as one. The optimized Z-Ant CMSIS wrapper, `cmsis_nn.qlinearconv`, explicitly extracts input and output tensors as NHWC and weights as OHWI, while `qlinearconvWithTranspose` exists precisely because older Z-Ant / ONNX flows are not naturally in that form. This is why layout is not merely a preprocessing preference; it is part of the actual callable contract of the CMSIS kernels. citeturn12view0turn14view2turn13view0 fileciteturn55file0L3-L3 fileciteturn62file0L3-L3

That layout point has a very practical consequence in the current branch. In `op_qlinearconv.zig`, the active CMSIS dispatch calls `cmsis_nn.qlinearconv()`, while a commented note still points to `nhwc_calculateOutputShape()` as a CMSIS testing path. At the same time, the project’s `CMSIS_GUIDE` tells users to generate an NHWC ONNX model for CMSIS, and it also documents a manual code edit if they want to use the transpose-based wrapper path instead. Taken together, those files show that the CMSIS integration is **not yet a transparent NCHW-to-CMSIS bridge by default**. It either expects CMSIS-friendly NHWC/OHWI inputs upstream, or it expects a deliberate manual switch to the transpose helper. That is one of the most important findings in this review. fileciteturn54file0L3-L3 fileciteturn56file0L3-L3 fileciteturn57file0L3-L3

The next formalism is **quantization contract**. Officially, the s8 convolution wrapper takes per-channel multiplier/shift arrays, an `int32` bias pointer, and signed input/output offsets in the ranges documented for `cmsis_nn_conv_params`. Z-Ant matches that contract by computing `scale_ratio = (x_scale * w_scale) / y_scale` per output channel, converting it into a CMSIS-style multiplier/shift pair, and then translating u8 ONNX-style zero-points into the s8 offset domain CMSIS expects by subtracting 128 when necessary. It also converts non-`i32` bias tensors into `i32` and repacks weights by subtracting per-channel weight zero-points and clamping to `i8`. When the weights are already symmetric `i8` with zero zero-point, the direct optimized path can skip that repacking and use the existing pointer. citeturn12view0 fileciteturn55file0L3-L3 fileciteturn56file0L3-L3

A concise way to express the current u8-to-s8 offset mapping used by Z-Ant is this:

```text
input_zero_point_s8  = input_zero_point_u8 - 128
cmsis_input_offset   = -input_zero_point_s8

output_zero_point_s8 = output_zero_point_u8 - 128
cmsis_output_offset  =  output_zero_point_s8
```

That mapping is important because CMSIS-NN’s public s8 convolution wrapper is documented around signed offsets, while the ONNX-facing side of Z-Ant may still be carrying unsigned activations. citeturn12view0 fileciteturn55file0L3-L3

Another indispensable formalism is **scratch/context management**. CMSIS-NN does not want the caller to guess temporary-memory sizes. The wrapper APIs are designed around a `cmsis_nn_context` whose size is obtained from the matching `*_get_buffer_size()` function. Z-Ant follows that rule correctly: it calls `arm_convolve_wrapper_s8_get_buffer_size()` or `arm_depthwise_conv_wrapper_s8_get_buffer_size()`, allocates the returned number of bytes, and then passes the resulting `cmsis_nn_context` into the wrapper call. Upstream CMSIS source confirms that these workspace formulas depend on the compiled backend path—MVE vs DSP vs pure C—and that some kernels reject a null context buffer when it is required. This is one of the reasons the CPU-selection flags discussed above are not just performance flags. fileciteturn55file0L3-L3 fileciteturn30file0L3-L3 fileciteturn50file0L3-L3 fileciteturn31file0L3-L3 citeturn12view0turn14view2

Grouped and depthwise convolution need special attention because they are **not** the same formalism in CMSIS-NN. In the current Z-Ant wrapper, standard convolution with `group == 1` calls `arm_convolve_wrapper_s8` directly. True grouped convolution is implemented as repeated sub-calls to the standard wrapper on sliced channel groups, followed by manual output interleaving. Depthwise convolution uses `arm_depthwise_conv_wrapper_s8` and a different filter layout, and the upstream depthwise wrapper documentation plus the buffer-size source both show assumptions around `input_dims->n == 1` for the optimized depthwise path. So if batched depthwise `QLinearConv` is part of the desired support surface, that constraint should be documented or enforced more explicitly in Z-Ant. fileciteturn55file0L3-L3 fileciteturn50file0L3-L3 citeturn14view2

Finally, there is the **toolchain and include formalism**. The current Z-Ant integration adds CMSIS-NN and CMSIS Core headers, CMSIS-DSP headers, and Arm newlib headers, and the CMSIS compiler header itself pulls in `arm_mve.h` for MVE builds and `arm_acle.h` for Arm intrinsics. Arm’s official README says CMSIS-NN is tested on Arm Compiler 6 and Arm GNU Toolchain and that host compilation is not supported out of the box. That warning matters here because Z-Ant’s build notes describe CMSIS support being linked even into host-side generators and tests for consistency. Structurally that is understandable, but from an upstream CMSIS point of view it is still outside the normal supported build model. fileciteturn51file0L3-L3 fileciteturn28file0L3-L3 fileciteturn27file0L3-L3 fileciteturn58file0L3-L3

## What is already present and what is still missing

For the **current** Cortex-M4 / Cortex-M7 style integration, the baseline load-bearing pieces are already there. The branch has a build-time CMSIS hook, real inclusion of the needed CMSIS convolution and support sources, explicit per-file C flags, LibC linkage, quantization-parameter generation, u8-to-s8 offset conversion, weight repacking and zero-copy shortcuts, scratch-buffer allocation via the official getter APIs, and actual dispatch into `arm_convolve_wrapper_s8` or `arm_depthwise_conv_wrapper_s8` depending on the convolution type. In other words, for the narrow target surface this branch was built around, it is more than a stub: it is a functioning integration scaffold. fileciteturn52file0L3-L3 fileciteturn51file0L3-L3 fileciteturn55file0L3-L3 fileciteturn29file0L3-L3 fileciteturn30file0L3-L3 fileciteturn50file0L3-L3

That said, **not all CMSIS-relevant flags and conditions are fully covered yet**.

The most important missing or incomplete items are these. First, the architecture gate is not real yet: `targetIsCortex` is hardcoded to `true`, so the compile-time dispatch is not actually checking whether the target is a supported Cortex-M architecture. Second, the current default dispatch calls the NHWC/OHWI-oriented `cmsis_nn.qlinearconv` path, while the transpose-based compatibility path exists but is not selected automatically; the project’s own guide still tells users to edit the code manually if they need that route. Third, the current build hook exposes only the four explicit C flags shown earlier; it does **not** expose Helium-oriented `ARM_MATH_AUTOVECTORIZE`, nor the optional CMSIS-NN requantization switches `CMSIS_NN_USE_SINGLE_ROUNDING` and `CMSIS_NN_USE_REQUANTIZE_INLINE_ASSEMBLY`. Fourth, `OPTIONAL_RESTRICT_KEYWORD` is currently applied unconditionally even though Arm’s own guidance is more nuanced by CPU family. fileciteturn53file0L3-L3 fileciteturn54file0L3-L3 fileciteturn57file0L3-L3 fileciteturn51file0L3-L3 fileciteturn27file0L3-L3

There are also some build-system hygiene gaps relative to current upstream CMSIS practice. The top-level CMSIS-NN `Source/CMakeLists.txt` and the subdirectory CMake files show that upstream expects CMSIS Core to be included as a dependency and, at the library level, tends to compile broad source globs for the convolution and support modules. Z-Ant instead maintains a hand-curated source list. That is fine for a targeted branch, but it is more brittle when upstream adds new support files or changes internal dependencies. Similarly, `cmsis_path` is currently commented out in `cmsis_flags.zig`, and `configureCmsisSupport()` sets `cmsis_path = null`, so the integration is presently biased toward a vendored `third_party` layout rather than a configurable external CMSIS installation. fileciteturn44file0L3-L3 fileciteturn45file0L3-L3 fileciteturn46file0L3-L3 fileciteturn59file0L3-L3 fileciteturn51file0L3-L3

There is one more subtle but important “not fully up-to-date with CMSIS” point: Arm’s current README still warns against `-ffreestanding` because of the implied builtin suppression, while the Z-Ant guide still shows `thumb-freestanding`. The branch’s `-fbuiltin` mitigation is sensible and probably sufficient for the current kernels, but it is still a deliberate workaround rather than a clean alignment with upstream recommendations. If the goal is a more robust long-term integration, it would be worth either isolating the CMSIS C compilation more explicitly from the freestanding policy or at least documenting this tradeoff clearly in the branch documentation. fileciteturn27file0L3-L3 fileciteturn57file0L3-L3 fileciteturn51file0L3-L3

The practical verdict is this: **for current Cortex-M4/M7 deployment on CMSIS-friendly NHWC/OHWI models, the essential explicit flags are mostly already present**. The missing pieces are less about those four baseline flags and more about architecture detection, layout-path selection, optional CMSIS configurability, and future-proofing. If I were tightening this branch for a successful and upstream-aligned integration, I would prioritize: replacing the hardcoded Cortex gate with a real target check, making the NCHW/NHWC choice explicit and automatic instead of manual, exposing `ARM_MATH_AUTOVECTORIZE` and the two optional CMSIS requantization switches as documented build knobs, making `OPTIONAL_RESTRICT_KEYWORD` conditional by CPU when desired, restoring a configurable CMSIS path option, and documenting or guarding the depthwise batch-size assumptions more strictly. fileciteturn53file0L3-L3 fileciteturn54file0L3-L3 fileciteturn57file0L3-L3 fileciteturn59file0L3-L3 fileciteturn50file0L3-L3 fileciteturn27file0L3-L3
